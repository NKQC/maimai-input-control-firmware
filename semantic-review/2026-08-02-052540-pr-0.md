# UI 串行 CSD 校准与频谱辅助调参（v3）

本次改动把全通道校准、基线复位和频率搜索改为 Host 逐通道编排，并加入单通道频谱、Cp 偏向、参数说明和遥测自愈。上一轮指出的 Prime 所有权、CSD 互斥、频谱归属、AUTO_TUNE 标签、批次代际和 telemetry freshness 问题已完成定向修复。终审仍确认三项阻塞缺陷：跨层完成语义取错、全局 IDAC 草稿未进入 Prime，以及逐通道搜索仍会重置其他通道状态。三端构建已有通过记录，但当前匹配镜像尚未刷写闭环。

**Watch for:** **[P1][confirmed]** CALIBRATE/BASELINE ACK 只确认 RP2040 异步入队，Host 却据此计成功并推进频谱；**[P1][confirmed]** 未保存的全局 IDAC 草稿不会成为批量 Prime 的来源；**[P1][confirmed]** 逐通道 AUTO_TUNE 每个通道完成后仍复位全部 36 通道基线；**[P2][confirmed]** 旧固件同步 AUTO_TUNE 响应没有先校验当前请求 seq；**[P2][confirmed]** 关键竞态和 GND/缺帧恢复仍未实机验证。

**Verdict**: NEEDS_CHANGES

## High-level view

**[P1][confirmed]** 校准与基线的完成语义仍停在 RP2040 入队层。Host 把受理 ACK 当作 PSoC 终态，因此批量结果、取消收敛和频谱采样都可能先于真实硬件结果。

**[P1][confirmed]** AutoTune 批次规划绕过草稿优先访问器，直接读取设备缓存。用户刚编辑但未保存的全局 IDAC 不会覆盖 36 个通道，Cp 偏向也会从旧档计算。

**[P1][confirmed]** Host 现在连续发起 36 次单通道搜索，但 PSoC 每次仍初始化全部基线；锁定增益恢复分支还可能重置全部 widget 状态。单通道协议已经贯通，底层状态副作用却仍是全局的。

**[P2][confirmed]** 新 AUTO_TUNE 推送会按 origin seq 拒绝陈旧帧，旧固件同步响应路径没有同等校验。迟到旧响应可清除当前请求归属，使随后合法结果被丢弃。

**[P2][confirmed]** 构建只能覆盖编译和链接；ACK/终态时序、非目标通道扰动、GND 延迟及缺帧自愈仍缺匹配硬件验证，不能作为发版闭环证据。

## CALIBRATE/BASELINE 的 ACK 停在 RP 队列层

Host 收到普通 ACK 后立即把批量通道记为 `Ok`，并让频谱 apply 步骤继续；完成文案甚至声称校准和基线“均已收到设备完成回执”（`control_software/src/app_state/mod.rs:6939-6954`; `control_software/src/app_state/ch_ops.rs:947-961`, `control_software/src/app_state/ch_ops.rs:1508-1525`, `control_software/src/app_state/ch_ops.rs:1600-1604`）。

RP 侧的实际契约不是完成回执。`Psoc::_submit` 对 `out == nullptr` 的写类命令异步入队即返回，`Psoc::calibrate` 和 `baseline_reset` 正使用该路径（`main_firmware/src/protocol/psoc/psoc.cpp:382-403`, `main_firmware/src/protocol/psoc/psoc.cpp:459-472`）；SensorLink 随即发送 ACK（`main_firmware/src/service/sensor_link/sensor_link.cpp:590-613`）。PSoC 的最终 `c.ok` 只留在 core1 槽位，没有终态帧返回 Host（`main_firmware/src/protocol/psoc/psoc.cpp:86-103`）。

```text
Host request
    |
    v
RP core0: enqueue core1 command ---- acceptance ACK ----> Host marks OK
    |
    v
RP core1 -> PSoC operation -> actual success/failure
                              (no terminal reply to Host)
```

**[P1][confirmed]** PSoC 失败仍会计入成功，频谱可能采样尚未生效的配置，取消或恢复也可能在 `heavy_busy()` 结束前释放控制面。RP 应在 core1/PSoC 形成真实结果后发送带原 seq 的终态 ACK/NAK；受理 ACK 必须单独建模，不能推进 `ChBatch` 或 `SweepApply`。

## 全局 IDAC 草稿没有进入批量 Prime

全局 IDAC 编辑调用 `global_set` 写入草稿，`global()` 才提供“草稿优先、设备缓存回退”的值（`control_software/src/main.rs:1159-1165`; `control_software/src/app_state/mod.rs:3610-3626`）。UI 回填使用了该 accessor（`control_software/src/main.rs:2415-2419`），但 AutoTune 批次规划和 Cp 偏向预览直接访问 `self.globals` 的设备回读值（`control_software/src/app_state/ch_ops.rs:649-665`, `control_software/src/app_state/ch_ops.rs:699-714`）。

**[P1][confirmed]** 编辑全局 IDAC 后直接搜索频率会把 36 个通道 Prime 成旧设备值，Cp 偏向也围绕旧档计算。批次开始时应通过 `self.global(GPARAM_IDAC_GAIN_INIT)` 读取并冻结本 generation 的起点档，避免未保存草稿丢失或扫描中途改变解释口径。

## 逐通道 AUTO_TUNE 仍有全通道副作用

Host 的全局搜索逐通道调用 `auto_tune_with_pref(ch, pref)`（`control_software/src/app_state/ch_ops.rs:880-903`）。PSoC 虽只对目标 widget 搜索（`psoc_firmware/CY8C4147AZI-SensorCore/main.c:1910-1921`），收尾却无条件调用 `Cy_CapSense_InitializeAllBaselines`（`psoc_firmware/CY8C4147AZI-SensorCore/main.c:1937-1944`），所以一轮全局搜索会重置全部通道基线 36 次。

单通道 CALIBRATE 在锁定档恢复分支还会调用全局 `Cy_CapSense_Initialize`（`psoc_firmware/CY8C4147AZI-SensorCore/main.c:1860-1874`）。该中间件入口初始化全部状态和整个 CAPSENSE 硬件（`psoc_firmware/mtb_shared/capsense/release-v5.0.0/cy_capsense_control.c:458-486`）。

**[P1][confirmed]** AUTO_TUNE 对其他 35 个通道的基线扰动无条件存在，锁定档被改回时还有额外的全 widget 状态重置。单通道收尾应只初始化目标 widget；锁定增益应用也应采用 widget 级路径，或保存并恢复非目标状态，再验证其 raw、baseline、diff 和 active 不跳变。

## 旧同步 AUTO_TUNE 响应绕过请求归属

新 `AUTO_TUNE_PROGRESS` 推送在写状态前会比较 `origin_seq` 与 `auto_tune_req_seq`（`control_software/src/app_state/mod.rs:5818-5838`）。旧固件同步 `HostCmd::AutoTune` 响应没有该前置检查，直接调用 `_apply_auto_tune_result`（`control_software/src/app_state/mod.rs:5793-5811`）；后者先无条件清空当前 `auto_tune_req_seq`，之后才对部分批次归因检查 seq（`control_software/src/app_state/mod.rs:5884-5949`）。

**[P2][confirmed]** 看门狗后到达的旧同步响应可清掉新请求归属并覆盖显示，随后合法推送会因归属为 `None` 被丢弃。同步兼容路径必须在应用前要求 `auto_tune_req_seq == Some(frame.seq)`，不匹配帧不得修改状态。

## 匹配硬件闭环仍缺失

已有记录覆盖 `cargo build --locked --bins`、`platformio run -e pico` 和 PSoC `make build -j8`，RP 产物嵌入的 PSoC 版本为 `0x9B733C23`、37504B，但未刷写当前匹配 RP/PSoC 组合。GND 变慢已有静态解释：建立时间从约 `172.5µs` 增至 `4386µs/通道`（`psoc_firmware/CY8C4147AZI-SensorCore/main.c:508-518`），代码默认改为 High-Z 但仍允许显式 GND。

**[P2][confirmed]** 现有证据没有覆盖真实 PSoC 完成相对受理 ACK 的时序、取消时 `heavy_busy` 收敛、非目标 baseline 扰动、未保存 IDAC 草稿 Prime、旧响应错序、6/12/16-bit rail、持续缺帧恢复以及 GND/High-Z A/B。修复三项 P1 后，应记录请求 seq、RP heavy 状态、PSoC busy、非目标 baseline、恢复后设备真值和同分辨率/分频下的每通道扫描周期。
